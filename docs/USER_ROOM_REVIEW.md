# 点亮中国 · 用户与房间系统重构方案（送审版）

> 2026-10-10 制定。背景：房间号易忘、成员名单与数据不一致 bug。Muse + agy 联合设计。
> 完整技术方案见 `docs/USER_ROOM_DESIGN.md`。

## 一、改动总览

| 模块 | 现状 | 改后 |
|---|---|---|
| 身份 | 浏览器本地成员档案（清缓存就丢） | 轻量用户 ID（UUID）+ 昵称，无密码；丢了可"认领"找回 |
| 足迹归属 | 跟着"房间里的成员"走 | 跟着"人"走，进哪个房间都带着 |
| 入口 | 打开即地图 | **待定**：A. 保持地图优先，大厅独立页面（agy 推荐）/ B. 进大厅 |
| 大厅（新增） | 无 | 个人主页：我是谁、我的房间列表、建房/加房按钮 |
| 房间 | 只有 6 位数字码 | 有名字（如"我们家"）、有房主；房主可改名/移人 |
| 加入房间 | 输码直接进 | 输码先预览（房间名+人数+成员昵称），确认再进 |
| 成员上限 | 6（前端）/ 4（Worker，不一致） | 统一 8 |
| 数据模型 | Store v4，KV 有 member 快照键 | Store v5；KV 只存 `user:{id}` 和 `room:{code}`，删快照键 |

## 二、关键决策（需拍板）

### D1：入口是大厅还是地图？
- **A（agy 推荐）**：保持打开即地图，大厅是右上角按钮进的独立页面。理由：现有习惯；大厅是低频操作。
- **B（你原想法）**：打开即大厅，一目了然，点一下进地图。
- 我的推荐：A。地图是高频，大厅是低频，别让低频挡高频。但大厅入口要做得显眼。

### D2：无密码身份，能接受吗？
- 方案：不做密码/OAuth，只靠设备 ID + 昵称。家庭信任模型下够用。
- 风险：拿到房间码的人能冒充他人认领（需二次确认+展示数据量缓解）。
- 我的推荐：接受。家庭应用，密码是过度设计。

### D3：房主权限是"纸糊"的，OK 吗？
- 无认证体系下，任何拿到房间码的人调 API 都能踢人/改名。UI 会明确提示，不暗示安全感。
- 我的推荐：接受，并如实告知用户。这是 6 位码分享机制的固有 trade-off。

## 三、分阶段实施

**Phase 1（核心）**：Store v5、大厅视图、建房/加入/预览卡、认领流程、新 Worker API（双语兼容旧客户端）、KV 数据迁移、配色补足到 8 色。
- 上线标准：542591 四人足迹迁移前后一致；旧客户端 24h 内同步正常。

**Phase 2（房间治理）**：改名、转让房主、移出成员、退出房间、空房删除、被踢感知。

**Phase 3（多设备）**：身份迁移码（换设备扫码认领）、重复身份合并工具。
