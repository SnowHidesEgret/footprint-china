# 点亮中国 · 用户系统重设计方案（v2）

> 状态：设计稿 v2.1（修订版），待用户拍板
> 日期：2026-10-11
> 修订说明：初稿把 KV 主键从 `userId` 改成 `username`，会导致足迹/房间两处大迁移；
> 本版改为"账号映射层"，userId 不变、房间模型不动，零数据迁移。
> 另：PK 不是新功能（见 §3.2），"昵称领回"有重名歧义（见 §3.4）。

---

## 一、为什么重设计

当前 v5 系统的问题：

1. **身份概念混乱**：「本机身份」vs「房间成员」两套并行（实测反馈"切换用户怎么都是我、逍逍、我"）
2. **无账号体系**：换浏览器靠"认领"找回，流程绕、容易出错
3. **游客和正式用户没区分**：所有人都是"本地档案"，权限无差别
4. **重复身份**：测试时产生多个"我"，无清理机制

用户要求（2026-10-11）：简单用户系统，需建账号、4 位数字密码；支持游客登录；
**登录态只保存在浏览器**；游客不能加入房间 PK。先设计，再实施。

## 二、新设计：两种身份

### 2.1 注册用户（正式账号）

| 项 | 说明 |
|---|---|
| 注册 | 账号名 + 4 位数字密码 |
| 账号名规则 | 2–12 字符，中文/字母/数字，**全站唯一**；即显示昵称（爸爸/妈妈/逍逍/遥遥） |
| 密码 | 4 位数字，注册时设置，可修改；服务端只存加盐哈希 |
| 登录态 | 只保存在本机浏览器 localStorage，下次打开自动登录；换设备用账号+密码登录即恢复 |
| 足迹 | 跟账号（userId）走，换设备登录即恢复，**不再需要"认领"** |
| 房间 | 可创建、可加入 |
| PK | 可参加（PK = 现有房间 PK 透视对比视图，见 §3.2） |

### 2.2 游客

| 项 | 说明 |
|---|---|
| 登录 | 一键"游客试玩"，无需注册 |
| 标识 | 系统生成 `游客_XXXX`（4 位随机），可改昵称（仅本地有效） |
| 存储 | **只在浏览器 localStorage，不上云**（符合"试玩"语义） |
| 足迹 | 只在本地；清缓存/换浏览器即消失，横幅会明示 |
| 房间 | **不能加入、不能创建**；大厅房间区替换为"注册后加入家庭房间"引导 |
| PK | 不能参加（进不了房间，自然没有 PK） |
| 转正 | 随时"注册为正式账号"，本机足迹一键并入新账号（规则同认领合并） |

**一句话**：游客 = 本机试玩，正式账号 = 长期用。

## 三、关键架构决策（本版定稿，不再讨论）

### 3.1 userId 不变，加"账号映射层"

初稿把 KV 主键改成 `user:{username}`，代价是足迹、房间成员两处重写。
本版方案：**内部主键仍是 userId（u_xxx/m_xxx），只加一层映射**：

```
acct:{username}  →  { userId, salt, pinHash, createdAt }
user:{userId}    →  保持 Phase 1 形状不变，新增字段 accountUsername（可空）
room:{code}      →  完全不变（memberUserIds 仍是 userId 数组）
```

好处：足迹数据零迁移、房间逻辑零改动、认领/合并规则复用。
代价：注册/登录多一次 KV 读（可接受）。

### 3.2 PK 不是新功能，不要重复造

`src/main.js` 已有 **PK 透视**（Phase 3）：房间成员足迹同屏对比，
单人独占显示成员色、多人同游金紫交辉高亮。用户说的"不能加入房间 PK"指的就是这个：
**游客不进房间 → 看不到房间成员 → 没有 PK 可参加**。本设计不新增任何 PK 功能，
只做权限门：游客隐藏房间入口与 PK 开关。

### 3.3 游客足迹不上云

与现状（所有档案都同步）不同，游客数据只走 localStorage：
实现上 `sync.js` 对 `kind:'guest'` 的 userId 跳过 PUT；转正时本机合并即可。
代价：游客清缓存丢数据——横幅明示"试玩数据只保存在本机"，可接受。

### 3.4 老用户迁移：本机一键绑定（不用"昵称领回"）

初稿方案"输入昵称+设密码领回"有致命歧义：昵称不唯一（两个"我"），
同名成员会抢错数据。本版方案：

- 老用户本机已有 userId + 云端足迹 → 大厅点 **"注册账号"** → 输入账号名+4 位密码
- 服务端：`acct:{username}→userId` 新建映射，`user:{userId}.accountUsername=username`
- **零歧义**：绑定的是本机已持有的 userId，不存在抢错；足迹原地继承，无需合并
- 之后换设备：账号+密码登录 → `GET /api/users/:userId` 拉回全部足迹

### 3.5 4 位密码的防暴力破解

4 位 = 1 万种组合，API 可被枚举。家庭小应用不做复杂风控，但底线要有：

- 登录接口限流：同一账号名 10 分钟内失败 5 次 → 锁定 10 分钟（429）
- 响应不区分"账号不存在"还是"密码错误"，统一 401（防账号枚举）
- 密码只存 `SHA-256(salt + pin)`，salt 随机 16 位 hex；Worker 用 Web Crypto 实现
- 不做图形验证码（家庭场景，限流够用）

### 3.6 两个"4 位密码"并存，UI 文案必须区分

今日（2026-10-11）刚上线**房间密码**（4 位数字，加入房间用）。
本设计新增**登录密码**（4 位数字，账号用）。两者正交，文案严格区分：

- 登录/注册页写"**登录密码**（4 位数字）"
- 建房/加房写"**房间密码**（4 位数字）"
- 加入框的"4 位按密码查房间"逻辑不变（那是房间密码通道）

## 四、登录流程

```
打开网站
  │
  ├─ 本机有登录态（users[] 非空）？
  │   ├─ 是 → 直接进地图（老习惯不变）；未绑定账号的老用户，大厅顶部提示"绑定账号，多设备同步"
  │   └─ 否 → 显示登录页（三选一）
  │         ├─ [账号登录] 账号名 + 登录密码（4 位）
  │         ├─ [注册账号] 账号名 + 登录密码 + 确认密码
  │         └─ [游客试玩] 一键进入
```

- 登录页**只在无本机身份时出现**（首次/退出后），不打扰老用户
- 注册用户登录态长期有效（除非主动"退出登录"）
- 一机多账号：登录页"切换账号"，本机可存多个账号会话（延续"全家共用一台平板"）
- 退出登录：只清 activeUserId，本机数据保留，重登秒恢复；
  另设"清除本机数据"（ destructive，二次确认）

## 五、房间与 PK 权限矩阵

| 操作 | 游客 | 注册用户（未绑定老用户视为注册用户） |
|---|---|---|
| 点亮地图（个人） | ✅（仅本机） | ✅（云端同步） |
| 浏览房间列表 | ❌（显示注册引导） | ✅ |
| 加入房间 | ❌（按钮不渲染，提示"注册后加入"） | ✅ |
| 创建房间 | ❌ | ✅ |
| 设/改房间密码 | ❌ | ✅（房主） |
| PK 透视开关 | ❌（不渲染） | ✅（房间内） |

服务端同样校验：`POST /api/rooms/:code/join` 查 `user:{userId}.accountUsername`，
为空（游客/未绑定）→ 403 `游客不能加入房间，请先注册`。前后端双保险。

## 六、数据模型

### 6.1 云端 KV（复用现有 ROOMS_KV，不新增 namespace）

```
acct:{username}          → { userId, salt, pinHash, createdAt }        // 新增
acct:rl:{username}       → { failCount, blockedUntil }                // 新增，限流用（TTL）
user:{userId}            → Phase 1 形状 + accountUsername（可空）      // 加字段
room:{code}              → 不变
pwd:{password}           → 不变（房间密码索引）
```

### 6.2 本地 localStorage（现有 key `footprint_china_v1_store`，version 5→6）

```jsonc
{
  "version": 6,
  "users": [
    {
      "userId": "u_kx3m9pq2",
      "kind": "user",            // 新增：user | guest
      "username": "爸爸",         // 新增：账号名；老用户 null = 未绑定
      "nickname": "爸爸",
      "color": "#C9A25E",
      "createdAt": 1791194398000,
      "updatedAt": 1791194398743
    }
  ],
  "activeUserId": "u_kx3m9pq2",   // 即登录态（只存浏览器）
  "footprints": { /* 不变；guest 的足迹只在本地，sync 跳过 PUT */ },
  "rooms": [ /* 不变 */ ],
  "activeRoomCode": "542591"
}
```

v5→v6 迁移：`kind` 默认为 `user`、`username` 默认为 null（= 未绑定老用户），
其余字段原样。游客新建时 `userId` 用 `g_` 前缀，与正式 `u_`/`m_` 区分。

## 七、API（Worker 新增，旧接口不动）

```
POST /api/accounts
  body: { username, pin }                        // 注册
  → 201 { userId } | 409 { error: '账号名已被使用' }
  说明：username 2–12 字符（中文/字母/数字）；pin 必须 /^\d{4}$/；
        新建 userId=u_xxx + user:{userId} + acct:{username}（事务性：先占 acct 键防并发重名）

POST /api/accounts/login
  body: { username, pin }
  → 200 { userId, nickname, color } | 401 { error: '账号或密码不正确' } | 429（限流）
  说明：成功后前端 GET /api/users/:userId 拉足迹；失败计数进 acct:rl:{username}

POST /api/accounts/bind
  body: { userId, username, pin }                 // 老用户本机一键绑定
  → 200 { ok: true } | 409（重名） | 404（userId 不存在）
  说明：user:{userId}.accountUsername = username；幂等（重复绑定同一 username 直接 ok）

PUT /api/accounts/pin
  body: { userId, username, oldPin, newPin }      // 改登录密码
  → 200 | 401

POST /api/rooms/:code/join
  body: { userId }（不变）
  → 新增 403：user:{userId}.accountUsername 为空 → { error: '游客不能加入房间，请先注册' }
```

密码找回（Phase 2，不在本期）：房主可在房间管理中为成员重置登录密码
（家庭信任模型；或暂不做 —— 待拍板 §11.3）。

## 八、老数据迁移

**结论：无需迁移脚本，零停机。**

1. 云端现有 `user:{m_xxx}` / `room:{code}` 原样不动（§6.1 只加字段、加键）
2. 前端 v5→v6 本地自动迁移（§6.2，纯加字段）
3. 老用户（542591 的爸爸/妈妈/逍逍/遥遥）：打开新版 → 一切如常 →
   大厅顶部出现一次性引导"绑定账号，换设备也能找回足迹" → 输入账号名+4 位密码 → 完成
4. 不绑定也能继续用（username=null），只是换设备仍需走旧认领流程
5. 部署顺序：Worker（新接口）→ 前端；旧前端无感知（新接口只是新增）

## 九、UI 变化

1. **新增登录页**：无本机身份时显示，三选一（账号登录 / 注册账号 / 游客试玩）；
   文案用"登录密码"，与"房间密码"区分（§3.6）
2. **大厅**：去掉"本机身份/切换档案"区（概念合并到账号；多账号走登录页"切换账号"）；
   未绑定老用户顶部显示一次性绑定引导；游客不渲染房间区，替换为注册引导卡
3. **游客横幅**：顶部小条"游客试玩中 · 数据只保存在本机 · [去注册]"（去注册=转正合并）
4. **PK 开关**：游客不渲染；注册用户进房间后照常显示
5. **退出登录**入口：大厅身份区（只清登录态，不清数据）

## 十、安全说明（家庭信任模型，延续 v1.0 立场）

- 4 位 PIN 防的是"熊孩子乱点"，不是黑客；**不要对外宣称安全**
- 房主/房间管理在无认证体系下依然是"便利性概念"（v1.0 §一.3 已有结论，本版不变）
- 登录限流（§3.5）是唯一新增的服务端防护；KV 中无明文密码
- 账号名全站唯一且房间内可见，提醒用户别用手机号等敏感信息做账号名

## 十一、待拍板（每条带推荐）

1. **游客是否可见房间列表/成员？**
   推荐：不可见，大厅房间区直接显示注册引导。理由：最简单、隐私面最小；
   游客点进房间也只能看不能动，徒增困惑。
2. **账号名与昵称合并还是分离？**
   推荐：合并（账号名=显示昵称，全站唯一）。理由：家庭小圈子，"爸爸"就是账号，
   少一个概念；重名时提示换一个（如"爸爸2"）。
3. **忘记登录密码怎么办？**
   推荐：房主可在房间管理中为成员重置（家庭信任，操作简单）。
   备选：暂不做，忘了就新建账号+认领合并（有兜底，不阻塞上线）。
4. **游客昵称允许修改吗？**
   推荐：允许，仅本地有效。理由：试玩改个名零成本。
5. **上线策略？**
   推荐：直接全量替换（家庭用户量小，出问题可快速回退到 v20261005t tag）。
   备选：双轨过渡（复杂度高，不推荐）。
